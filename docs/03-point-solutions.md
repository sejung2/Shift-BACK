# 포인트 갱신 손실 해결

## 후보

- 어떤 방법들을 검토했나?
    - 낙관적 락
    - 조건부 UPDATE
    - synchronized
    - 비관적 락

## 문제 지점과 해결 방향

- 읽기 / 계산 / 쓰기 중 각 방법은 어디를 막나?
    - 낙관적 락은 쓰기 순간에 읽은 뒤로 바뀌었는지 확인해서 막음
    - 조건부 UPDATE는 계산을 DB에 맡겨서 계산 구간을 없앰
    - synchronized는 읽기~쓰기 전체를 한 스레드씩 실행하게 함. 단 락이 커밋 전에 풀려서 뚫림
    - 비관적 락은 읽을 때 DB 행을 잠그고 커밋할 때 풀어서 읽기~쓰기 전체를 막음

## 실험 결과

조건: 포인트 1000, 100원 주문 10건 동시 결제

|                      | 낙관적 락        | 조건부 UPDATE                           |
|----------------------|------------------|-----------------------------------------|
| 성공 / 실패          | 1건 / 9건        | 10건 / 0건                              |
| 최종 포인트          | 900 (1건만 결제) | 0 (전부 결제)                           |
| 주문의 remain_points | 900 (맞음)       | 10건 모두 900 (틀림. 900~0이 찍혀야 함) |

- 조건부 UPDATE의 remain_points가 틀린 이유: UPDATE 전에 읽어 둔 엔티티 값으로 계산해서. UPDATE 후 다시 조회하면 고칠 수 있음

## 선택: 낙관적 락

- 왜 골랐나? (충돌 빈도 기준으로)
    - 충돌 가능성이 적은 경우이기 때문
- 조건부 UPDATE는 언제 더 나은가?
    - 선착순 쿠폰 발급이나 많은 사람들이 동시에 같은 값을 깎는 경우에

## 동작 원리

- @Version이 붙으면 UPDATE 문이 어떻게 바뀌나?
    - where절 끝에 version 조건이 추가됨
    - 성공하면 version이 1 올라감
    - 그 사이 누가 먼저 바꿔서 조건이 안 맞으면 바뀐 행이 0개 → 예외 발생 → 롤백

## 테스트 검증 방법

- 왜 "0이 되냐"가 아니라 "성공 수 × 100"으로 검사했나?
    - 낙관적 락을 사용하면 몇 건이 성공할지 모르기 때문
- 왜 AtomicInteger를 썼나?
    - 람다는 다른 스레드에서 나중에 실행돼서 지역변수를 복사해 감. 복사본을 바꿔도 의미가 없어서 자바가 막음
    - count값 조차도 스레드들이 동시에 접근하면 동시성 문제가 발생하기 때문

## 낙관적 락만으로 안 되는 것 (작성 예정)

- 충돌로 실패한 요청은 사용자에게 어떻게 보이나?
- 결제 연타 / 중복 결제

## 헷갈렸던 것

- 실패 8개, 남은 포인트 0, 테스트 통과라고 예측했음
    - 실패가 8개면 2건만 성공이라 800이 남아야 함 실패 수와 남은 포인트는 같이 움직임


- @Version 한 줄로 어떻게 막는지 몰랐음
    - JPA가 UPDATE 문을 만들 때 version 조건을 알아서 붙임


- @Version이 @Transactional 밑에 붙는 줄 알았음
    - @Transactional은 서비스 메서드, @Version은 엔티티 필드에 붙음


- 성공한 결제 수를 굳이 왜 세는지 몰랐음
    - 같은 900이라도 10건 결제 (버그)와 1건 결제 (정상)가 있어서 숫자 하나로는 구분이 안 됨


- 낙관적 락이 테스트의 count도 막아주는 줄 알았음
    - 락은 DB 행만 지킴 자바 변수는 별개


- 조건부 UPDATE가 틀린 기록을 남겨서 쓸모없다고 생각했음
    - 다시 조회하면 고칠 수 있는 문제임 진짜 차이는 충돌 때 실패하냐 안 하냐


- 동시성을 막으려면 락이 꼭 필요한 줄 알았음
    - 조건부 UPDATE처럼 락 없이 계산을 DB에 맡기는 방법도 있음


- 결제 연타도 낙관적 락으로 막히는 줄 알았음
    - 동시에 들어온 건 막지만 시간차로 들어오면 통과함 중복 결제는 주문 상태 확인으로 따로 막아야 함


- 장바구니로 묶이니까 서로 다른 결제가 동시에 올 일이 없다고 생각했음
    - 드물 뿐 없지 않음. 선물 결제, 결제 중 환불, 다른 기기 동시 결제
