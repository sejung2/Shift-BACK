# 로그아웃·탈퇴한 토큰 차단 (Redis 블랙리스트)

## 1. 문제
로그아웃하면 서버는 DB의 Refresh Token만 지우고 Access Token은 그대로 둔다.
그래서 로그아웃한 뒤에도 같은 Access Token으로 만료될 때까지(최대 30분) 요청할 수 있었다.

탈퇴는 막히고 있었다. 필터가 매 요청 DB에서 사용자를 조회하고, `@SQLRestriction` 때문에 탈퇴한 사용자는 조회되지 않아 401이 나갔다.
대신 탈퇴 하나를 막으려고 모든 요청이 DB를 한 번씩 조회하고 있었다.

## 2. 왜 JWT만으로는 못 막나
서버는 Access Token을 저장하지 않는다. 서명과 만료 시간만 보고 통과시킨다.
그래서 클라이언트가 토큰을 지워도, 누가 미리 복사해 갔다면 그 복사본은 만료될 때까지 통과한다.

로그아웃 코드에 있던 `SecurityContextHolder.clearContext()`도 효과가 없었다.
로그인 정보는 요청마다 따로 만들어진다. 같은 토큰으로 다시 요청하면 필터가 토큰을 보고 로그인 정보를 다시 채운다.

## 3. 검토한 방법
| 방법 | 장점 | 단점 |
|---|---|---|
| Access Token 수명을 아주 짧게 | 추가 저장소가 필요 없다 | 그 짧은 시간 동안은 여전히 뚫린다. 재발급 요청이 늘어난다 |
| 토큰 버전 (users 테이블에 버전 숫자) | Redis 없이 DB만으로 된다 | 로그아웃하면 그 사용자의 모든 기기가 같이 로그아웃된다 |
| Redis 블랙리스트 | 토큰 하나 단위로 막을 수 있다 | Redis라는 저장소가 하나 늘어난다 |

여러 기기 로그인을 허용할 계획이라, 기기 하나만 로그아웃시킬 수 있는 블랙리스트를 골랐다.

## 4. 설계
| 상황 | 블랙리스트에 넣는 것 | 유지 시간 |
|---|---|---|
| 로그아웃 | 그 Access Token | 토큰의 남은 시간 |
| 탈퇴 | 사용자 ID | Access Token 최대 수명(30분) |

로그아웃에 사용자 ID를 넣으면, 로그아웃하고 바로 다시 로그인해서 받은 새 토큰까지 막힌다. 그래서 토큰 하나만 넣는다.
탈퇴는 다른 기기나 복사된 토큰까지 전부 막아야 한다. 탈퇴한 사람은 다시 로그인할 일이 없어서 사용자 ID를 넣어도 문제가 없다.

유지 시간은 토큰이 어차피 만료되는 시점까지만 둔다. 만료된 토큰은 블랙리스트가 없어도 서명 검사에서 걸린다.
로그아웃은 그 토큰의 남은 시간만, 탈퇴는 그 직전에 발급된 토큰까지 막아야 해서 최대 수명만큼 둔다.

필터의 DB 조회는 없애고 블랙리스트 확인으로 바꿨다. 탈퇴가 블랙리스트로 막히기 때문에 DB 조회가 필요 없어졌다.

## 5. Redis가 죽으면
필터는 매 요청 Redis에 블랙리스트를 물어본다. Redis가 죽으면 이 확인을 못 한다.

이때 요청을 통과시키면 로그아웃한 토큰과 탈퇴한 사용자의 토큰이 다시 쓰일 수 있다.
그래서 통과시키지 않고 막기로 했다.

막을 때는 401이 아니라 503(서비스 일시 불가)으로 응답한다.
프론트는 401을 받으면 토큰 문제로 보고 재발급을 시도하고, 실패하면 로그아웃시킨다.
Redis가 죽은 건 서버 문제인데 401로 막으면 멀쩡한 사용자까지 전부 로그아웃된다.

필터에서 블랙리스트를 확인하다가 Redis 쪽 예외(`DataAccessException`)가 나면 잡아서 바로 503을 응답하고, 요청을 더 진행하지 않는다.

## 6. 검증
고치기 전에 문제를 재현하는 테스트를 먼저 만들고, 고친 뒤 통과하는지 확인했다.

| 상황 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 로그아웃한 토큰으로 요청 | 200 | 401 |
| 탈퇴한 사용자의 토큰으로 요청 | 401 (DB 조회로 막힘) | 401 (블랙리스트로 막힘) |
| Redis에 연결할 수 없을 때 | 예외가 그대로 터짐 (500) | 503 |

모든 테스트에서 막혀야 하는 경우와 통과해야 하는 경우를 같이 확인했다.
예를 들어 로그아웃 테스트는 로그아웃 전에 같은 토큰으로 정상 응답이 오는 것부터 확인한다.
토큰이 처음부터 안 먹혀도 401은 나오기 때문에, 이 확인이 없으면 아무것도 안 고쳐도 테스트가 통과한다.

탈퇴 테스트는 처음에 테스트 환경 때문에 엉뚱하게 실패했다.
테스트 클래스에 `@Transactional`이 붙어 있어서 로그인, 탈퇴, 다음 요청이 같은 영속성 컨텍스트를 썼다.
그래서 탈퇴한 뒤에도 필터가 DB가 아니라 캐시에 남은 사용자를 꺼내 "있다"고 판단했다.
실제 서버는 요청마다 따로 동작하기 때문에, `@Transactional`을 빼고 테스트가 끝나면 직접 데이터를 지우도록 바꿨다.

## 7. 같이 고친 것
필터가 토큰 종류를 확인하지 않고 있었다. 서명과 만료 시간만 봤다.
Access Token과 Refresh Token은 같은 키로 서명되기 때문에, Refresh Token을 Access Token 자리에 넣어도 통과했다. Refresh Token은 수명이 7일이라 더 위험하다.

토큰에 들어 있는 종류 값(`type`)이 `access`인 경우에만 로그인 처리하도록 바꿨다.
Refresh Token으로 요청하면 이제 401이 나간다. 정상 Access Token은 그대로 통과하는 것도 같이 확인했다.

## 8. 한계
- 로그아웃은 그 토큰 하나만 막는다. 다른 기기의 Access Token은 최대 30분 동안 계속 쓸 수 있다.
- 필터가 더 이상 DB를 보지 않는다. 앞으로 계정 정지 같은 기능을 만들면 블랙리스트에 직접 넣어야 막힌다.
- Redis는 DB 트랜잭션과 따로 동작한다. 탈퇴 중에 블랙리스트에 넣은 뒤 DB가 롤백되면, 탈퇴는 안 됐는데 토큰은 막힌다.
  그래서 블랙리스트에 넣는 작업을 탈퇴 처리 맨 끝에 뒀다. 커밋이 끝난 뒤에 실행되도록 바꾸는 방법(`@TransactionalEventListener`)이 있다.
- Redis가 오래 죽어 있으면 그동안 로그인이 필요한 모든 요청이 503이 된다.
  운영이라면 Redis를 복제본과 자동 전환 구성으로 두고, 재시작해도 블랙리스트가 남도록 디스크에 저장하는 것이 먼저다.
