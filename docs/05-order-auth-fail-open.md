# 주문 API 인증 누락 (fail-open) 보완

## 1. 문제
로그인 안 한 사람, 즉 uid가 null인 사람은 `if (uid != null && ...)` 조건 때문에 소유자 검사를 그냥 통과했다.
리팩토링 전에는 조회, 결제, 결제 결과, 취소가 이렇게 되어 있었다.
결제는 주문에 저장된 senderId로 사용자를 찾기 때문에, 주문번호만 알면 남의 포인트로 결제를 진행시킬 수 있는 구조였다.

환불은 소유자 검사 자체가 빠져 있어서 로그인한 사용자가 남의 주문을 환불할 수도 있었다.

## 2. 왜 지금까지 문제가 안 됐나
SecurityConfig가 permitAll로 연 경로를 빼고 `anyRequest().authenticated()`로 나머지를 전부 막고 있다.
`/orders/**`는 열린 목록에 없어서, 로그인하지 않은 요청은 서비스까지 오지 못한다.

## 3. 그래도 고친 이유
필터가 막아주는 건 지금 설정이 그대로일 때만이다. 이런 경우엔 서비스까지 그대로 들어온다.
- 누군가 주문 경로를 permitAll로 열었을 때
- HTTP를 거치지 않고 다른 코드(스케줄러, 다른 서비스)에서 서비스를 바로 부를 때

fail-open은 확인이 안 될 때 통과시키고, fail-closed는 거절한다.
원래 코드는 uid가 null이면 검사를 건너뛰는 fail-open이었고, 이걸 fail-closed로 바꿨다.

## 4. 해결
조회, 결제, 결제 결과, 취소에서 uid를 꺼내는 메서드를 `getUserIdOrNull()`에서 `getUserId()`로 바꿨다.
`getUserId()`는 로그인 정보가 없으면 예외를 던지기 때문에, 그 아래 소유자 검사까지 왔다면 uid는 null이 아니다.
그래서 `uid != null &&` 조건을 지우고 소유자인지만 확인한다.

환불에는 같은 방식으로 uid를 꺼내고 소유자 검사를 새로 넣었다. 본인 주문이 아니면 `AccessDeniedException`을 던진다.

## 5. 검증
- 로그인하지 않은 상태(`clearContext`)에서 결제하면 `BadRequestException`이 나고 포인트는 그대로인지 확인
- 다른 사용자로 로그인(`loginAs(-1L)`)해서 남의 주문을 환불하면 `AccessDeniedException`이 나고 포인트는 그대로인지 확인

예외만 보지 않고 포인트도 같이 확인했다. 예외는 거절했다는 신호일 뿐이고, 실제로 데이터가 안 바뀌었는지는 따로 봐야 하기 때문이다.

## 6. 헷갈렸던 것
테스트를 고칠 때 메인 스레드에서 로그인시켰는데도, 스레드 풀 안에서 부른 서비스는 로그인 정보가 없다고 실패했다.
`SecurityContextHolder`는 로그인 정보를 스레드마다 따로 저장(ThreadLocal)하기 때문에, 메인 스레드의 로그인 정보가 풀 스레드에는 없었다.

처음엔 람다마다 `loginAs()`를 넣으려 했지만, 반복이 많고 하나라도 빠뜨리면 그 테스트만 깨진다.
대신 `DelegatingSecurityContextExecutorService`로 스레드 풀을 감쌌다. submit할 때 메인 스레드의 로그인 정보를 작업에 넘기고, 끝나면 지워준다.

`MODE_INHERITABLETHREADLOCAL`(자식 스레드가 부모의 로그인 정보를 물려받는 방식)은 쓰지 않았다.
스레드 풀은 스레드를 재사용하기 때문에, 처음 물려받은 로그인 정보가 남아서 다른 사용자로 실행될 수 있다.

## 7. 남은 문제
같은 패턴이 남아 있는지 OrderService에서 `getUserIdOrNull`을 쓰는 곳을 다시 확인했다.

- `createPointOrder` (금액권 주문 생성): 요청에 들어온 senderId를 로그인 정보보다 먼저 쓴다.
  로그인한 사용자가 senderId에 다른 사람 ID를 넣으면 그 사람 이름으로 주문이 만들어진다.
  로그인한 요청이라 필터도 통과하기 때문에 지금도 실제로 가능하다.
- `createOrder` (주문 생성): uid가 null이면 요청에 들어온 senderId를 그대로 쓴다.
  비로그인 요청은 필터가 막고 있어서 지금은 문제가 되지 않지만, 구조는 1번과 같은 fail-open이다.

두 곳 모두 senderId를 요청에서 받지 않고 로그인 정보로만 정하도록 고칠 예정이다.
