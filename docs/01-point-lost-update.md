# 포인트 결제 갱신 손실 재현

## 문제 상황
- 어떤 기능에서?
    - 포인트 결제 기능에서 문제 발생
- 어떤 조건에서 터지나?
    - 같은 사용자의 결제 요청 여러 개가 동시에 들어올 때

## 원래 코드의 흐름
- requestPayment는 포인트를 어떤 순서로 처리하나?
    - 조회 → 검증 → 서비스 로직에서 잔액 계산 → 계산한 값으로 덮어쓰기

## 왜 터지나
- 두 요청이 동시에 들어오면 각자 무슨 값을 읽나?
    - 아직 아무도 커밋하지 않은 시점이라 10개 요청이 전부 포인트 1000을 읽음
    - 각자 포인트(1000 - 100 = 900)를 계산해서 덮어씀. 그래서 마지막에 누가 쓰든 900
- @Transactional이 있는데 왜 못 막나?
    - 트랜잭션은 각자 작업만 독립적으로 보호하는 거지 줄 서서 기다리게 하는 게 아님
    - 일반 SELECT는 락을 안 걸어서 다른 트랜잭션도 같은 값을 읽을 수 있음

## 재현 방법
- 테스트 조건 (포인트, 주문 개수, 금액)
    - 포인트: 1000, 주문 개수: 10, 금액: 100
- 왜 스레드를 썼나 / 왜 CountDownLatch가 필요했나
    - 동시에 여러 요청들이 들어오는 상황을 재현하기 위해
    - 메인 스레드가 다른 스레드들의 동작을 건너뛰지 않고 기다리기 위해

## 결과
- 기대값: 0
- 실제값: 1회차: 900, 2회차: 900
- 이게 실제 서비스에서 왜 심각한가?
    - 1000원어치 결제됐는데 포인트는 100만 차감됨. 900원어치를 공짜로 쓴 것
    - 포인트 사용 기록은 10건(합계 1000)인데 실제 잔액은 900. 장부와 잔액이 안 맞음

## 헷갈렸던 것
- 트랜잭션이 걸려 있으면 A가 도는 동안 B가 간섭 못 한다고 생각했음
    - 실제로는 각자 독립적으로 돌 뿐이고 같은 값을 동시에 읽을 수 있었음
- synchronized를 붙이면 동시성 문제는 해결된다고 생각했음
    - 실제로는 메서드가 끝나면서 락이 풀리고, 커밋은 그 뒤에 스프링 프록시가 해서 그 사이에 다른 요청이 들어옴
- shutdown()과 await() 차이
    - shutdown()은 새 작업을 안 받을 뿐 돌고 있는 작업이 끝날 때까지 기다려주지 않음
    - await()는 CountDownLatch 카운트가 0이 될 때까지 대기
